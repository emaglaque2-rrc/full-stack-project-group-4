# Sprint 1 Retrospective 

## What went well in the sprint

The project setup was easy and quick to follow, as it was mostly similar to what I did for Lab 1.2.
I was assigned the User Inventory feature. I was able to create the user data JSON file, which includes user information such as the user ID, name, email, and rental history. 
This gave me a good starting point for the User Inventory feature and helped me understand how the rental information would be organized.
Another thing that went well was navigating through GitHub and creating separate branches for my feature work. 
Having separate branches helped me stay organized and keep my changes separate from the main project.
The other thing that went well was the group coordination and teamwork. I really appreciated my teammates working together, 
helping each other when we ran into issues, and staying on track with the project requirements.

## What could have gone better in the sprint

The Vercel deployment could have gone better. In the beginning, it seemed to work well, but when we tried to push our changes, it started showing errors and I was blocked from deploying.
 My teammate was able to troubleshoot the issue and realized that it was happening because the repository was private. After the repository was made public, 
 I was able to successfully deploy the project on Vercel.
Another thing that could have gone better was my planning for the STYLEGUIDE.md. I was not completely sure what information needed to be included, 
so I struggled with deciding which specific styling requirements to document. This took more time than I expected.
There were also some merge conflicts during the sprint, although they were not too serious. I realized that I need to be more careful when working with multiple branches.
 At one point, I accidentally made commits on the wrong branch and pushed some changes to a branch that I did not intend to use.

## What can be done in the next sprint to improve my process

In the next sprint, before starting my development work, I will make a short plan listing the files I need to work on and what needs to be completed in each file. 
I will use this plan at the beginning of the sprint and update it as I complete each task. This will help me avoid working on too many files or branches 
at the same time and reduce the chance of making changes on the wrong branch.
I will also test my changes locally before creating a Pull Request for each feature. My goal is to make sure the feature works as expected locally and that 
there are no obvious errors before asking a teammate to review it. I will do this for every Pull Request I create during the next sprint so that fewer issues are
 carried into the review and merge process.Finally, I will work on one feature branch at a time whenever possible and verify my current branch before committing 
 or pushing changes. I will check the branch name before each commit and push throughout the next sprint. This will help prevent the branch mix-ups I experienced during 
 this sprint and make the team's Git workflow smoother.
